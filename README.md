# Документация по лабораторной работе: Настройка статического IPsec-туннеля (Традиционный WAN)

## 1. Цель работы
Настроить статический IPsec-туннель между двумя удаленными филиалами с использованием Libreswan. Продемонстрировать работоспособность защищенного соединения в штатном режиме и зафиксировать последствия разрыва канала связи, выявив ключевые недостатки традиционного WAN-подхода.

## 2. Схема сети и адресация
В лабораторной среде развернуты два узла, имитирующие граничные маршрутизаторы филиалов.

| Параметр | Branch A | Branch B |
|----------|----------|----------|
| Внешний IP-адрес (WAN) | 192.168.3.168 | 192.168.3.194 |
| Внутренняя подсеть (LAN) | 10.0.1.0/24 | 10.0.2.0/24 |
| IP шлюза LAN | 10.0.1.1 | 10.0.2.1 |
| Роль в туннеле | Левая сторона (Left) | Правая сторона (Right) |

Туннель инкапсулирует трафик между подсетями `10.0.1.0/24` и `10.0.2.0/24`.

## 3. Настройка IPsec-туннеля

Конфигурация выполняется на базе Libreswan (IKEv2, PSK-аутентификация). Файлы размещаются в директории `/etc/ipsec.d/`.

### 3.1. Конфигурация Branch A
Файл: `/etc/ipsec.d/tunnel-to-branchB.conf`
```bash
conn branchA-to-branchB
    type=tunnel
    left=192.168.3.168
    leftsubnet=10.0.1.0/24
    leftid=192.168.3.168
    right=192.168.3.194
    rightsubnet=10.0.2.0/24
    rightid=192.168.3.194
    authby=secret
    auto=start
    ike=aes256-sha2-modp2048
    esp=aes256-sha2
    leftsendcert=never
    rightsendcert=never
```

### 3.2. Конфигурация Branch B
Файл: `/etc/ipsec.d/tunnel-to-branchA.conf`
```bash
conn branchB-to-branchA
    type=tunnel
    left=192.168.3.194
    leftsubnet=10.0.2.0/24
    leftid=192.168.3.194
    right=192.168.3.168
    rightsubnet=10.0.1.0/24
    rightid=192.168.3.168
    authby=secret
    auto=start
    ike=aes256-sha2-modp2048
    esp=aes256-sha2
    leftsendcert=never
    rightsendcert=never
```

### 3.3. Ключевые параметры
- `type=tunnel`: Режим полного туннелирования IP-пакетов.
- `authby=secret`: Использование заранее распределенного ключа (Pre-Shared Key).
- `auto=start`: Попытка установления туннеля при запуске службы.
- `ike`/`esp`: Шифрование AES-256, хеширование SHA-2, группа DH modp2048.
- `leftsendcert`/`rightsendcert=never`: Отключение проверки сертификатов для упрощения PSK-аутентификации.

## 4. Проверка работоспособности (Штатный режим)

### 4.1. Статус службы IPsec
Выполнена команда `ipsec status`. Вывод подтверждает успешное согласование фаз IKEv2:
```
Connection list:
"branchB-to-branchA": 10.0.2.0/24===192.168.3.194[+S-C]...192.168.3.168[+S-C]===10.0.1.0/24; erouted; eroute owner: #3

State Information:
#1: "branchB-to-branchA":500 STATE_V2_ESTABLISHED_IKE_SA (established IKE SA)
#2: "branchB-to-branchA":500 STATE_V2_ESTABLISHED_CHILD_SA (established Child SA)
#3: "branchB-to-branchA":500 STATE_V2_ESTABLISHED_CHILD_SA (established Child SA); eroute owner
```
Статусы `STATE_V2_ESTABLISHED_IKE_SA` и `STATE_V2_ESTABLISHED_CHILD_SA` указывают на успешное создание защищенного канала. Флаг `eroute owner` означает, что маршрут для подсети зарегистрирован в ядре.

С узла Branch B отправлены ICMP-запросы к шлюзу Branch A через внутренний интерфейс:

## 5. Демонстрация отказа канала

Для имитации аварии физический или виртуальный интерфейс WAN был отключен (или связь разорвана на уровне L2/L3).

### 5.1. Попытка отправки трафика после разрыва
```bash
ping -c 4 -I 10.0.2.1 10.0.1.1
```
Результат:
```
ping: bind: невозможно назначить запрошенный адрес
```
Система не может привязать сокет к внутреннему IP для маршрутизации через недоступный внешний интерфейс.

При повторной попытке без привязки к интерфейсу:
```
PING 10.0.1.1 (10.0.1.1) 56(124) bytes of data.

--- 10.0.1.1 ping statistics ---
4 packets transmitted, 0 received, 100% packet loss, time 16395ms
```

### 5.2. Состояние IPsec после сбоя
Традиционный статический туннель не поддерживает динамическое переключение. При падении канала:
- IKE SA переходит в состояние ожидания или постоянного пересогласования (`STATE_V2_REKEYING` / `HOLD`).
- Child SA помечается как неактивный, маршрут удаляется из таблицы маршрутизации ядра.
- Автоматический поиск альтернативного пути отсутствует. Восстановление требует ручного вмешательства администратора или переконфигурации маршрутизации.

## 6. Анализ недостатков традиционного WAN

На основе проведенного эксперимента выявлены следующие ограничения статического IPsec-подхода:

1. Отсутствие автоматического Failover
Туннель жестко привязан к конкретному внешнему IP-адресу и интерфейсу. При потере связности по основному каналу трафик не перенаправляется автоматически на резервные линии. Время простоя определяется только скоростью реакции администратора.

2. Статическая маршрутизация
Маршруты к удаленным подсетям прописываются вручную или создаются демоном IPsec на основе фиксированных параметров `left`/`right`. Система не оценивает текущее состояние канала (задержку, джиттер, потери пакетов) и не принимает решений на основе метрик качества.

3. Отсутствие мониторинга в реальном времени
Традиционная реализация Libreswan отслеживает состояние SA только через механизмы Dead Peer Detection (DPD), которые предназначены для обнаружения полного разрыва, а не для анализа деградации канала. Падение производительности или частичные потери не триггерят переключение.

4. Сложность масштабирования
При добавлении новых филиалов или резервных каналов требуется ручное создание дополнительных конфигураций `conn`, обновление ACL и перезагрузка службы. Конфигурация становится громоздкой и подверженной ошибкам при росте топологии.

## 7. Выводы
Лабораторная работа подтвердила, что статический IPsec-туннель обеспечивает надежное шифрование трафика в штатном режиме, но обладает критическими недостатками в условиях нестабильных каналов связи. Разрыв единственного активного интерфейса приводит к полной потере связности между филиалами без возможности автоматического восстановления. Данный сценарий демонстрирует необходимость перехода к архитектурам SD-WAN, где механизмы динамического выбора пути, непрерывный мониторинг качества каналов и автоматический failover встроены в базовую логику работы сети.
